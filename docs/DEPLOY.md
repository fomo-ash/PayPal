# Deploy to Render (free) and register the PayPal webhook

One free web service plus free Postgres, from `render.yaml`. The API runs in single-process
mode: grading, PayPal capture/void/payout and the timers run inside the web process, files live
in Postgres, and migrations run on every start. No Celery, Redis or paid worker needed.

Verified before shipping (Nov 9): the exact start command against Postgres 16 with a
`postgres://` URL ran migrations to 0003, validated a suite in E2B (spec check 20/20) and created
a real PayPal sandbox order. The full test suite passes on Postgres.

## 1. Create the blueprint

1. Push your branch, then open <https://dashboard.render.com> → **New** → **Blueprint**.
2. Connect the GitHub repo and pick the branch that has this `render.yaml`.
3. Render shows `verdict-api` (web, free) and `verdict-db` (Postgres, free). Fill the secrets it
   asks for, copying values from your local `.env`:

| Key | From `.env` |
|---|---|
| `PAYPAL_CLIENT_ID`, `PAYPAL_SECRET` | same |
| `SANDBOX_WORKER_EMAIL` | same |
| `E2B_API_KEY` | same |
| `LLM_API_KEY`, `LLM_FALLBACK_API_KEY` | same |
| `RECEIPT_SIGNING_KEY_B64` | same (so receipts verify with the same key) |
| `PAYPAL_WEBHOOK_ID` | leave empty for now (step 3) |

`SESSION_SECRET` and `DEV_AUTH_TOKEN` are generated by Render. `DATABASE_URL` is wired from `verdict-db`.

4. **Apply**. The first build takes a few minutes. When it is live, open
   `https://<your-service>.onrender.com/health` → `{"ok": true}`, and `/docs` for the API.

The free web service sleeps after 15 minutes idle and takes ~1 minute to wake. Open `/health`
a minute before a demo.

## 2. Register the webhook in PayPal

1. <https://developer.paypal.com> → **Apps & Credentials** → your sandbox app → **Sandbox
   Webhooks** → **Add Webhook**.
2. Webhook URL: `https://<your-service>.onrender.com/webhooks/paypal`
3. Event types: tick the ones listed in `SUBSCRIBED_EVENTS`
   (`backend/verdict/paypal/webhooks.py`), or simply **All events**; events Verdict does not use are
   acknowledged and ignored. The important ones: `CHECKOUT.ORDER.APPROVED`,
   `PAYMENT.AUTHORIZATION.CREATED`, `PAYMENT.AUTHORIZATION.VOIDED`, `PAYMENT.CAPTURE.COMPLETED`,
   `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.PAYOUTSBATCH.SUCCESS`,
   `PAYMENT.PAYOUTSBATCH.DENIED`, the `PAYMENT.PAYOUTS-ITEM.*` events, and
   `CUSTOMER.DISPUTE.CREATED` / `UPDATED`.
4. Save, then copy the **Webhook ID** PayPal shows.

## 3. Give the webhook ID to the API

Render → `verdict-api` → **Environment** → set `PAYPAL_WEBHOOK_ID` → **Save** (it redeploys).
Every event is then verified with PayPal and stored once; webhooks never move money.

## 4. Point the demo at the deployed API

The dev login (`/dev/users`, `X-User-Id`) is locked on the public URL: every dev call must also
send `X-Dev-Token`. Copy `DEV_AUTH_TOKEN` from Render → `verdict-api` → **Environment**:

```bash
export VERDICT_API_URL=https://<your-service>.onrender.com
export VERDICT_DEV_TOKEN=<DEV_AUTH_TOKEN from Render>
python scripts/demo_flow.py
VERDICT_AGENT_KEY=vk_... make agent
```

Agent keys (`vk_...`) and PayPal logins do not need the token. Validation is limited to
`VALIDATE_PER_HOUR` (12) and example runs to `EXAMPLES_RUNS_PER_HOUR` (60) per user, so a visitor
cannot burn the E2B and LLM credits.

## When the web app is deployed

Add these to `verdict-api` so PayPal sends buyers back to the web app and the browser may call
the API: `CORS_ORIGINS`, `PAYPAL_RETURN_URL`, `PAYPAL_CANCEL_URL`, `PAYPAL_LOGIN_REDIRECT_URI`
(the last one must also be the Return URL in the app's Log in with PayPal settings). Then set
`DEV_AUTH=false` so only PayPal logins work on the public URL.
